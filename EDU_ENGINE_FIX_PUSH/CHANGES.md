# Medical-emergency legal fix — push pack contents

Scope grew from the originally-requested single file to four — the two prescribed `defendable_analyser_v3.html` edits alone didn't change what the live engine actually shows (see below). All four files go to the **repository root**, overwriting existing files of the same name.

## Files to upload (overwrite existing)

- **defendable_analyser_v3.html** — the two edits as specified: `LEGAL_CHAR.medical` rewritten to DEFEND-with-evidence (LE v TAP C-74/19 analogy); `RM_DB`'s `medical` node (`limb1Status` → `'extraordinary'`, `limb1` text, `caselaw` array, `caselawIds`) rewritten to match. `crew-sick`'s narrow upstream-extraordinary-event carve-out promoted into `limb1` — `limb1Status` untouched, still `'unlikely'`. Also bumped two script-tag cache-busting versions (`defendable_registry.js?v=sessC1`, `defendable_trees.js?v=sessC3`) — both were unversioned, so the browser was serving stale cached copies of them throughout testing until this was added; without it, this whole fix would silently not appear for anyone with those files already cached.
- **defendable_trees.js** — `DT-09` (the actual decision tree the live "Provisional position" panel runs — separate from the LEGAL_CHAR/RM_DB data, discovered during verification) restructured from a hardcoded NOT-EC/concede tree to a DEFEND-track tree: entry → foreseeability check → **concede** only if crew ignored obvious pre-boarding signs, otherwise → **EC established** (LE v TAP C-74/19 analogy, Air Navigation Order / ICAO Annex 6 mandatory duty) → standard reasonable-measures gate. Also fixed two bugs found in the process, both pre-existing and unrelated to the medical position itself: (1) `DT-09`'s own keyword matching used `\bmedical` with no trailing word boundary, so it silently matched "medically" inside unrelated crew-illness narrative — tightened to `\bmedical\b` throughout; (2) `DT-06` (crew-sick's own tree)'s entry gates didn't recognise "Captain **reported** sick" phrasing or "FDP" (only "FTL"), so it was falling through to the wrong tree — broadened both patterns. Neither of these was visible before because DT-09 used to default to CONCEDE regardless, which happened to mask both bugs; fixing DT-09's position correctly is what exposed them.
- **defendable_registry.js** — `DT-09`'s conclusion-id metadata (`DT9_MEDICAL_ORDINARY_CONCEDE`/`DT9_MEDICAL_SAFETY_JUDGMENT`) renamed to `DT9_MEDICAL_EXTERNAL_EC`/`DT9_MEDICAL_FORESEEABLE_CONCEDE` to match the restructured tree. Confirmed via grep these ids aren't referenced anywhere else before renaming.
- **defendable_demo_v2.js** — its own separate, hardcoded `medical()` demo causal-chain (verdict, per-event EC flags, DT-09 node text) updated to the same DEFEND position for consistency. **Not loaded by `defendable_analyser_v3.html`** (confirmed — no script tag references it there), so it wasn't exercised by live verification; included because it's the same legal position duplicated in a fourth place and would otherwise be left contradicting the fix if some other page uses it.

## Why this grew beyond the two named edits

Verifying live (`loadScenario('medical')` → `runAnalysis()` → `confirmLineOfFlying()`) after the two prescribed edits still showed **"No EC defence"** — the "Provisional position" panel doesn't read `LEGAL_CHAR`/`RM_DB` at all for this scenario; it runs the separate `DT-09` decision tree in `defendable_trees.js`, which had its own independent, hardcoded "not EC" reasoning. Fixing that surfaced two further pre-existing bugs (above) that were previously invisible because they happened to coincide with the old, incorrect answer.
